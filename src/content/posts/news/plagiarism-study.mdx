How much of the maker’s work in software projects in the unified database shows evidence of reuse from existing code?

## Process

### Context

Similarity analysis is one way of answering this question. Similarity alone cannot establish code reuse, but substantial and distinctive similarity can be evidence of reuse, especially when examined in context. This approach is used by various plagiarism detection systems such as Turnitin, which identifies similarities for educators to review ([source](https://guides.turnitin.com/hc/en-us/articles/34400565079053-Turnitin-and-plagiarism)).

In my experience, people frequently use code from three sources: tutorials, answers and repositories. Repositories are easy to search (e.g. GitHub's code search, Sourcegraph, grep.app...), whereas tutorials and answers... not so much (requiring scraping or figuring out how to compare code snippets against whole projects). But code from popular public resources frequently makes its way to public repositories, which means these can act as a proxy corpus.  
This study targeted software projects and checked for similarities between project code and public repositories.

### Candidate Selection

For candidate selection, the project was checked out at a pre-approval date and 30 lines were randomly picked, with ineligible lines being rerolled. The following conditions were checked to determine eligibility:

* not a library import (e.g. “import requests”)  
* not an overly common line (e.g. "break", "return")  
* not empty (i.e. contains at least one alphanumeric character)

These lines were used as search queries in GitHub's code search API. The resulting repositories were scored using the number of hits, while taking the number of query results and the repository's position in the result ranking into account to promote rarer lines.  
Both candidates before and after the project were considered and categorized accordingly. Candidates predating the project could show that the matching code existed publicly before project submission, whereas candidates after the project could be useful since repositories were also being treated as a proxy corpus: code from tutorials, answers or other sources could appear in a public repository afterwards.  
Up to 10 pre-project and up to 3 post-project results were selected as candidates.

### Filtering

After the candidate selection and comparison design were finalized, the data was filtered:

* GPT 5.6 Luna classified projects by type using their descriptions. All non-software projects were filtered out.  
* Language data for all remaining repositories was acquired. All projects whose dominant language was not Python were filtered out.

After these two stages, there were still more than 2000 projects left. Since processing was very time-consuming, 200 projects were picked at random.

### Comparisons

There were three main code similarity analysis tools: MOSS, Dolos and JPlag. Of these, only JPlag supported project comparisons. However, JPlag only supported specific languages (such as Java, C, C++, C\#, Go, Kotlin, Python, R, Rust, Scala, Swift, JavaScript, TypeScript, LLVM IR, and Scheme), and adding support for new languages was a costly process, to say the least.  
Language distribution in the dataset was analyzed, and it was found that JavaScript was the most prevalent language, by several measures: "language appears in repository", "more than 50% of code belongs to language" and "most code in repository is language". However, after looking into it, I found out that this was because of the many JavaScript variants, such as JSX (not supported by JPlag). In the end, I focused on one language only for simplicity. I chose Python, the second most prevalent language, as it did not have the same variant problem as JavaScript.  
Analyses were run with a minimum match length of 24 tokens. Dependencies and Python virtual environments were filtered out.  
After analysis, due to JPlag’s frequent false positives, GPT 5.6 Luna classified matches according to the following categories:

| Question | Details | Options |
| :---- | :---- | :---- |
| Is there meaningful overlap? | Does the code look sufficiently similar, or is it completely unrelated? | **yes**, **no** |
| What type of overlap is it? |  | **generated\_or\_vendored\_code**: code generated by third-party tools, such as Django or Alembic migrations<br/>**template\_or\_starter\_code**: template code, e.g. Django scaffolding<br/>**common\_idiom**: overlap is present, but the implementation is conventional (with few significant, distinctive shared characteristics)<br/>**distinctive\_shared\_code**: significant, distinctive shared code |
| Is external resource usage suspected? | To answer this question, the AI reviewer is instructed to look for:<br/>1. References to other repositories<br/>2. Overlap of non-generic distinctive code, which would have been unlikely to arise independently, suggesting usage of external resources such as tutorials, forum answers or other repositories. The candidate repository could be one such external resource. | **explicit**: the maker explicitly credits an external resource, and the code suggests usage of external resources<br/>**suspected**: the code suggests usage of external resources<br/>**none**: external resource usage seems unlikely |

## Methodology

1. Get all projects from the Unified Database  
2. Classify projects into "software", "hardware" or "unknown", with a confidence level, using the description  
3. Filter out non-software projects  
4. Fetch repository language data from GitHub  
5. Filter out all projects which do not have Python as the dominant language  
6. Pick 200 projects at random  
7. For each project:  
   1. Pick 30 random lines and search for them on GitHub  
   2. Order results by number of queries in which they appear, considering ranking and query result count  
   3. Clone the first 10 pre-project repositories and the first 3 post-project repositories  
   4. Run JPlag against the project and the cloned repositories  
   5. Record chronology  
   6. Classify overlap using AI

## Results

200 projects were selected, of which 180 were successfully analyzed. The remaining 20 could not be analyzed, for example, because they were too large or did not have Python as the dominant language at the time of approval.

Generated or vendored code was excluded from all coverage/project statistics, as it is not part of the maker’s work. Reuse was defined as code which appears to have been derived from an external resource, rather than written independently. In practice, this refers to matches classified as external usage.

Across all analyzed projects, 3.03% of tokens were covered by matches with code in repositories predating the project. Considering only reuse matches, the coverage was 2.64%.

Some example projects include:

* **Project A** is a tic-tac-toe game with a 100% pre-project match with a tutorial repository, and the maker credits the author of the tutorial "for this idea". It was approved three weeks ago.  
* **Project B** is a CLI with a 97.20% pre-project match with an unrelated repository, which does not frame itself as an educational resource. As an aside, this project consists of 91 lines, with 31 approved hours — the combination of all three factors suggests something amiss. This project was approved two years ago.  
* **Project C** is among many Haxmas workshop submissions with high match percentages, having a 100% pre-project match with another Haxmas submission.

> Project is plagiarized from another source (tutorial with no modifications, stolen code, copy of a previous project with little/no modifications, etc.)  
> - [YSWS Project Submission Guidelines](https://hackclub.gitbook.io/ysws-project-submission-guidelines/BLBRN8LIfoCZhFV6oMNR/spot-checks)  

Before drawing any conclusions, I think it's important to look at the current rules on plagiarism and tutorial use, which I wholeheartedly agree with. Putting plagiarism aside, beginner coders need educational resources to be able to get started. However, mindlessly copying tutorials without understanding them doesn't help them get started and shouldn't be rewarded. There's also a fairness aspect: if person A, who follows a tutorial 1:1, receives the same credit as person B, who plans and designs their own project, there's far less incentive to make truly creative projects, which is what Hack Club is all about.

Having said that, the good news is that most analyzed projects showed no detected overlap with pre-existing work. The less good news is that a small number showed substantial overlap with existing work, including cases that appear to be incompatible with the guidelines described above. The results of this study suggest three things:

* More weight should be given to plagiarism and appropriate use of tutorials. Currently, these are mentioned in one sentence on the Spot-Checks page in the YSWS Project Submission Guidelines.  
* An "external resource disclosure" field should be introduced, and the contents of this field should be validated by reviewers (formalizing the requirement in the guidelines and going hand in hand with point 1). This would be a low-cost way of addressing “non-malicious” plagiarism, wherein the author discloses their sources, thereby allowing cases such as Project A to be caught.  
* Quality & Integrity should look into ways of detecting these cases.

## Limitations

* The pipeline is less likely to detect small matches, hence the low number of projects classified as "trace" or "some". The absence of matches does not imply originality; it simply shows that this analysis pipeline was unable to detect any evidence of reuse.  
* A limited subset of Python software projects was analyzed, which is not fully representative of all software projects.  
* Only repositories which were public at the time of the study were analyzed.
